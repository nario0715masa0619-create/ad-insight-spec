# CampaignPilot 事業検証プラン

このドキュメントは、CampaignPilot の議論を**インフラ整備から事業検証へ戻す**ために作成した。
主題は「作れるか」ではなく、**「需要があるか」「顧客が金を払う価値があるか」**である。
PostgreSQL/Cloud SQL関連の話（[postgresql_hosting_decision_memo.md](postgresql_hosting_decision_memo.md)等）は、
実査運用に不可欠な範囲（案件記録の保存先など）でのみ触れる。

---

## 1. 背景

CampaignPilotはこれまで「広告・LP・KPIを横断して診断し、改善アクションを判断するための仕組み」として
実装が進み、営業資料（[campaignpilot_sales_doc.md](../campaignpilot_sales_doc.md)、
[campaignpilot_sales_talk_advanced.md](../campaignpilot_sales_talk_advanced.md)、
[campaignpilot_talk_script.md](../campaignpilot_talk_script.md)）も整備された。

これらの資料は「改善判断にかかる時間を減らせる」「担当者依存を減らせる」という価値を主張している。
しかし、これらは**現時点では検証されていない仮説**であり、実際に運用者が違う行動を取るのか、
その行動が成果につながるのか、顧客がそれに対価を払う意思を持つのかは、まだ確認できていない。

一方で、この仮説を検証するための仕組み（[verification機能](../../backend/app/models/verification.py)）は
既にmainに実装済みである。案件ごとの事前ヒアリング内容、CampaignPilot提示後の評価、提案ごとの
「気づき度」「独自性」評価、2週間後・4週間後のフォローアップ、CSV出力までが一通り揃っている
（詳細は「10. 既存資料・既存機能との関係」）。

**今、足りていないのはコードではなく、この仕組みを使って実際に何件・誰に対して・どう検証し、
何が出れば成功/失敗と判断するのかという実査プランそのものである。**

---

## 2. いま本当に検証すべきこと

営業資料は「時間短縮」「属人化解消」を訴求しているが、これらは**間接指標**である。
本当に検証すべきは、もっと手前にある3つの問いである。

1. **CampaignPilotを見た運用者は、Meta Ads Manager単体では取らなかった行動を取るか**
   （見えるようになった、ではなく、行動が変わったか）
2. **その行動変化は、成果改善または工数削減につながるか**
   （行動が変わっても、結果が変わらなければ価値ではない）
3. **顧客はそれに対して金を払う意思を持つか**
   （良い感想ではなく、購買の意思決定）

「見える化」自体は価値ではない。**Meta Ads Managerの管理画面だけを眺めていても、多くの数値は
既に「見えて」いる。CampaignPilotの価値は、見えている情報から人が出す打ち手そのものを変えられるかにある。**

---

## 3. 検証仮説

| 仮説 | 内容 |
|---|---|
| H1（新規性仮説） | CampaignPilotの提案の一定割合は、Meta Ads Managerの数値だけを見ていては運用者が自力で気づけない、または優先度を上げられない内容である |
| H2（実行仮説） | 「言われて初めて気づいた」提案は、実際に実行に移される |
| H3（成果仮説） | 実行された提案は、2〜4週間後に成果改善（CPA/CVR/CTR等）または工数削減として観測できる |
| H4（購買意思仮説） | 上記が確認できた運用者・意思決定者は、無償の感想ではなく、有償（または値引き有償）での継続利用に前向きになる |

H1〜H4はすべて連鎖している。**H1が成立しなければH2以降は測る意味がなく、H1〜H3が崩れた状態でH4だけを
聞いても、社交辞令の好意的回答しか得られない。** 実査は必ずH1から順に確認する設計とする。

一般論の改善提案（「クリエイティブをA/Bテストしましょう」等、誰でも言える内容）が中心になった場合、
それはH1の不成立であり、後続の指標がどう出ても**事業として失敗**とみなす。

---

## 4. 成功条件 / 失敗条件

### 成功条件（すべて満たすことを目指す。一部のみでも部分的な前進として記録する）

- 運用者が、CampaignPilotの提案の少なくとも一部について
  「Meta Ads Managerだけではこの判断に至らなかった」と認める（H1）
- CampaignPilotの提案から、具体的な改善アクションが実際に実行される（H2）
- 2〜4週間後に、成果差または工数差が観測される（自己申告・実測いずれでも可、ただし区別して記録する）（H3）
- 運用者または意思決定者が、無償の好意ではなく、有償／値引き有償での継続利用に前向きな意思を示す（H4）

### 失敗条件（いずれか複数が該当した場合、そのアカウントでは「価値未実証」と判定する）

- 提案が見やすいだけで、判断材料としての新規性がない（毎回「一般論」「自分でも出していた」評価が中心）
- 実行されない（「実行しにくい」「不要」評価が中心、またはfollowupで`executed=false`が続く）
- 実行されても、成果差・工数差が観測されない
- 課金意思がない（「無料なら使う」「参考程度」という回答が中心）

**成功条件・失敗条件のどちらとも言い切れない「中間」の結果は正直に中間として記録する。
無理に成功/失敗どちらかに寄せない。**

---

## 5. 実査対象の選定基準

- 対象は**3〜5案件**を目安とする（人間が判断すべき点として後述）
- 選定基準:
  - 実際にMeta広告を継続運用しており、直近のKPIデータが取得できる案件
  - 運用担当者・意思決定者へのヒアリングアクセスが確保できる案件
  - 業種・広告予算規模に極端な偏りがないこと（可能な範囲で）
- **除外基準**:
  - CampaignPilotの開発チーム自身が運用している案件（自己評価バイアスを避ける）
  - 既にCampaignPilotの存在・提案内容を知っている案件（新規性評価が歪む）

---

## 6. ヒアリング対象者と役割

CampaignPilotの価値は、聞く相手によって評価軸が異なる。役割を分けて記録する。

| 役割 | 主な関心 | 聞くべきこと |
|---|---|---|
| **運用者**（実務担当） | 日々の判断・工数 | 提案の新規性、実行のしやすさ、日々の工数感覚の変化 |
| **マネージャー**（チーム責任者） | 判断の再現性・属人化 | 担当者交代時の引き継ぎやすさ、チーム内の判断のばらつき |
| **経済購買者**（費用の意思決定者） | ROI・投資対効果 | 成果差・工数削減の金額換算、継続利用への支払い意思 |

**運用者だけにヒアリングして「良かった」で終わらせない。** 特にH4（課金意思仮説）は、
運用者の感想ではなく、実際に費用を判断する経済購買者の反応で測る。運用者とマネージャー/経済購買者が
同一人物の場合はその旨を記録する。

---

## 7. 実査フロー

既存の[verification機能](../../backend/app/models/verification.py)（`/api/v1/verification/*`）を実査記録の
基盤として使う。以下の流れは、既存機能の各エンティティに対応させて設計している。

```
1. 案件選定（5章の基準で選ぶ）
        │
2. 事前ヒアリング（VerificationCase.pre_hearing_notes に記録）
   - 現状の課題認識
   - Meta広告運用歴・現状の運用状況
   - CampaignPilotに期待すること
        │
3. CampaignPilot提示（既存の分析結果 asset_id / asset_version を紐付け）
        │
4. 提示直後の評価（VerificationCase.presentation_evaluation に記録）
   - 全体的な有用度（第一印象。ただしこの時点の評価は参考値に留める＝社交辞令が混じりやすいため）
        │
5. 提案ごとの評価（VerificationSuggestionEvaluation に記録）
   - 気づき度: 既に気づいていた / 言われて初めて気づいた / 妥当性に疑問 / 判断不能
   - 独自性: 自分でも出していた / 自分では先に出せなかった / 一般論 / 実行しにくい / 不要
   - ※ここがH1の主要データ
        │
6. 実行追跡（2〜4週間）
        │
7. 2週間後フォローアップ（VerificationFollowup, checkpoint=week_2）
   - 実行有無
   - 成果変化（自由記述）
        │
8. 4週間後フォローアップ（VerificationFollowup, checkpoint=week_4）
   - 実行有無
   - 成果変化（自由記述）
        │
9. 経済購買者への課金意思ヒアリング（別途、後述の「9. 有償パイロット判定条件」参照）
        │
10. 案件ごとの判定 → 全案件の集計 → 有償パイロット判断
```

---

## 8. 評価指標

既存機能で直接取得できる指標と、ヒアリングで別途取得が必要な指標を分けて示す。

### 既存機能（verification API / CSV出力）で直接集計できる指標

| 指標 | 算出方法 |
|---|---|
| **「自分では出せなかった」提案割合** | `originality_rating = could_not_have_suggested_myself` の件数 ÷ 全提案評価件数 |
| **提案実行率** | `VerificationFollowup.executed = true` の件数 ÷ フォローアップ記録件数（week_2/week_4それぞれで算出） |
| **新規性×実行の交差** | `awareness_rating = realized_when_told` かつ `executed = true` の件数（=「言われて気づき、実際にやった」件数） |

### ヒアリングで別途取得が必要な指標（現状のverification機能のスキーマには専用フィールドが無い）

| 指標 | 取得方法 |
|---|---|
| **実行後改善率** | `VerificationFollowup.result_change`（自由記述）を、事前KPIと突き合わせて定性/定量判定する。現状は自由記述のみのため、判定は人手で行う |
| **工数削減の自己申告/観測値** | 別途ヒアリングで「導入前と比べて判断にかかる時間がどう変わったか」を聞き、記録する（現状のスキーマ外。当面はヒアリングメモとして`pre_hearing_notes`または別記録に残す） |
| **有償パイロット移行率** | 対象案件のうち、実際に有償パイロットへ進んだ件数 ÷ 実査対象件数 |
| **継続意思率** | ヒアリングで「今の内容なら有償でも使い続けたいか」を直接聞き、Yes/No/条件付きで記録する |

**この指標整理自体が、verification機能に「工数削減」「課金意思」「継続意思」を記録する専用フィールドが
無いという設計上のギャップを明らかにしている。** 今回はコード変更を行わないため、当面は自由記述欄や
別途のヒアリングメモで代替し、実査を先に始める。専用フィールド追加が必要かどうかは、実際に3〜5件の
実査を回してから判断する（今スキーマを拡張するのは時期尚早）。

---

## 9. 有償パイロット判定条件

以下をすべて満たした場合に、有償パイロットへの移行を検討する。

1. 実査対象案件の**過半数**で、「自分では出せなかった」提案が1件以上存在する（H1の最低ライン）
2. そのうち**半数以上**で、実際に提案が実行に移されている（H2）
3. 実行された提案のうち、**一定数**で成果改善または工数削減が観測される（H3。「一定数」の具体的な閾値は
   実査対象件数が少ないため、実査開始前に固定の割合を決め打ちせず、実際の結果を見て判断する）
4. **経済購買者**（運用者ではない）から、有償または値引き有償での継続利用に前向きな反応が得られる（H4）

上記を満たさない場合は、**有償パイロットへ進まず、提案の作り方・提示の仕方・対象案件の選び方を
見直すフェーズに戻る**。無理に有償化を急がない。

---

## 10. 実査完了後に出すべき意思決定

実査完了後、以下のいずれかを判断できる状態にする。

- **A. 有償パイロットへ進む**（9章の条件を満たした場合）
- **B. 提案内容・提示方法を見直して再実査する**（H1〜H2は成立したがH3が弱い等、部分的成功の場合）
- **C. 現状の形では価値が実証できず、機能の作り方自体を見直す**（H1が成立しない、一般論中心の場合）

いずれの場合も、判断の根拠を8章の指標とヒアリング記録に基づいて明文化する。
「なんとなく手応えがあった」という感覚だけで有償パイロットに進まない。

## 11. 今は後回しでよいもの

- PostgreSQLへのインフラ移行（[Issue #80](https://github.com/nario0715masa0619-create/ad-insight-spec/issues/80)以下）:
  実査自体は現行のSQLite運用で問題なく回せる。実査記録件数はごく少数（3〜5案件）であり、
  インフラのボトルネックにはならない
- verification機能のスキーマ拡張（工数削減・課金意思・継続意思の専用フィールド化）:
  8章で指摘した通り、まず実査を回してから、本当に専用フィールドが必要かを判断する
- UI改善・自動集計ダッシュボード化: 3〜5件規模であれば、CSV出力＋手動集計で十分。
  件数が増えてから検討する

## まとめ: 次に人間が判断すべきこと

**3〜5件の実査対象案件を、5章の選定基準（Meta広告継続運用中・KPIデータ取得可能・
ヒアリングアクセス確保・CampaignPilot未認知）で選び、実査を開始してよいか。**

これが決まれば、7章の実査フローに沿って事前ヒアリングから着手できる。
