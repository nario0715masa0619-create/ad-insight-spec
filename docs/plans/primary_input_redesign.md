# CampaignPilot 主入力の再定義（CSV + クリエイティブ + LP）

## 背景・目的

CampaignPilotのプロダクト価値は「Meta広告運用の意思決定を速くする」ことにあります。
これまでのUI・docsは「KPIを入力して分析するツール」という手入力中心の見え方をしていましたが、
数値（CSV）だけでは「なぜ数値が悪化したか」（クリエイティブの訴求が弱いのか、LPとの接続が
悪いのか）という原因分析の本丸には踏み込めません。

本ドキュメントは、CampaignPilotの主入力を以下の3点に再定義し、UI・バックエンド・分析フロー・
docsをそれに合わせて整えた設計判断を記録します。

## 入力の再定義

### 主入力（3点）

1. **Meta Ads CSV** — 数値の根拠（CTR/CPC/CVR/CPA/spend等の傾向）
2. **広告クリエイティブ（動画または画像）** — 訴求・表現の根拠
3. **LP（URL）** — 遷移先体験の根拠

### 補助入力

- 目標KPI・商材/オファー概要・補足メモ・今回特に見てほしい論点
- KPI手入力（JSON） — **CSVが手元にない場合の補助的な入力手段**（廃止ではなく格下げ）

### 例外入力（fallback）

- クリエイティブなし（広告面のみ分析）… **今回は未実装**（後述「スコープ判断」参照）
- LPなしでの広告面のみ分析 … `file_plus_kpi`モードとして実装
- 数値なしでの簡易分析 … `file_only`/`file_plus_lp`モードとして実装

## 分析パターン（`mode`）の再整理

既存の3モード（`file_only` / `file_plus_lp` / `file_plus_lp_plus_manual_kpi`）に加えて、
新たに `file_plus_kpi`（クリエイティブ + CSV/KPI、LPなし）を追加しました。

| UI表示 | `mode`値 | 必須入力 | クレジット | 位置づけ |
|---|---|---|---:|---|
| 🌟 標準（推奨）: CSV + クリエイティブ + LP | `file_plus_lp_plus_manual_kpi` | クリエイティブ + LP + CSV/KPI | 3 | **本命**。広告〜LPのボトルネック分析まで踏み込める |
| CSV + クリエイティブ（LPなし・広告面分析） | `file_plus_kpi`（新規） | クリエイティブ + CSV/KPI | 2 | 数値と訴求表現の接続が見える。LPが無い/対象外の場合 |
| クリエイティブ + LP（数値なし・簡易） | `file_plus_lp` | クリエイティブ + LP | 2 | 数値が無い場合の簡易分析 |
| クリエイティブのみ（最小・簡易） | `file_only` | クリエイティブのみ | 1 | 最小構成、fallback |

既存3モードの技術的な値・バリデーション契約（`AdInsightSpec.validate_mode_requirements`）・
クレジット消費量は**変更していません**（後方互換性維持）。`file_plus_kpi`は完全に新規追加の
モードであり、既存モードの意味・挙動には影響しません。

## スコープ判断: 「CSVのみ（クリエイティブなし）」は今回実装していません

> **follow-up整理済み**: この論点は独立したIssue・設計メモとして切り出しました。
> 詳細な技術的根拠・実装論点・リスク・推奨方針は
> [csv_only_mode_followup.md](./csv_only_mode_followup.md) を参照してください。

タスク定義では「CSVのみ」を最も軽量なfallbackモードとして位置づけていましたが、
**本タスクでは実装していません。** 理由:

- `AnalysisOrchestrator._step_ingest()` は現在、クリエイティブファイル（`input_path`）を
  構造的に必須としています。`_step_metadata` / `_step_content_analysis`（動画フレーム抽出・
  OCR）/ `_step_llm`（クリエイティブ画像/テキストを前提にしたLLM呼び出し）まで、一貫して
  「クリエイティブが存在する」前提でパイプラインが組まれています。
- 「クリエイティブなしでCSVだけ受け付ける」ためには、これらのステップすべてに
  クリエイティブ不在の分岐を追加する必要があり、影響範囲が大きく、OCR/動画解析ロジック
  自体の変更も伴いかねません（今回のタスクで明示的にスコープ外とされた領域に踏み込む）。
- 一方、「CSV + クリエイティブ + LPなし」（`file_plus_kpi`）と「クリエイティブ + LPのみ
  （数値なし）」（`file_plus_lp`）は、既存のConverterService（`landing_page`/`performance`
  いずれも独立してoptional）がそのまま対応できる構造だったため、**新モード1つの追加**という
  最小差分で実現できました。

**将来この制約を外す場合の見取り図**: `_step_ingest`をoptionalにし、`_step_metadata`が
クリエイティブ不在時のフォールバックのasset_meta（CSVのcampaign_name/adset_name/ad_name由来）を
組み立てられるようにし、`_step_content_analysis`/`_step_llm`をクリエイティブ有無で完全に
分岐させる、という3段階の変更が必要になる見込みです。

## クリエイティブの複数アップロード対応

「1案件につき動画1本〜画像数枚」という実装上の考え方に対応するため、Streamlit UIの
クリエイティブアップローダーを`accept_multiple_files=True`に変更しました。

**設計判断**: バックエンドの分析パイプライン自体（1リクエスト=1クリエイティブ）は変更せず、
**UI側で複数ファイルをループしてリクエストを送る**方式にしました。

- 理由: `AnalysisOrchestrator`を「複数クリエイティブを1度に解釈する」構造へ変更すると、
  LLMプロンプト構成・OCR・動画処理など既存ロジックへの影響が大きく、「最小差分で段階的に
  移行できる設計にする」という原則から外れます。
- 効果: 同じCSV/LPの文脈を共有したまま、クリエイティブごとに個別のAdInsightレコードとして
  保存されます（`asset_name`には自動で連番を付与）。「保存済み結果」タブから各クリエイティブの
  分析結果を個別に確認できます。
- 将来の拡張余地: 複数クリエイティブを横断した比較分析（例: どのクリエイティブが最も
  効いているか）を行う場合は、`asset_id`同士を束ねる「案件」概念の導入が必要になります
  （厳密な広告ID紐付けは今回スコープ外、「今回やらないこと」に明記済み）。

## LP入力: URL対応の追加

これまで`/api/v1/specs/analyze`の`lp_file`パラメータはHTMLファイルのアップロードのみを
受け付けていましたが、`LPService.execute()`自体は元々URL（http/https）とローカルファイルパスの
両方に対応していました（バックエンド内部では既にURL対応済みだったが、API層に配線されていな
かった）。

今回、新しい`lp_url`フォームパラメータ（文字列）を追加し、Streamlit UI側もLP入力方法を
「LP URL（推奨）」「LPファイルをアップロード（HTML）」の選択式にしました。`lp_url`と`lp_file`が
両方指定された場合は`lp_url`を優先します（ファイル保存自体を行わない）。

## 手入力KPIの位置づけ変更

`file_plus_lp_plus_manual_kpi`モード内のKPI入力方法（Meta Ads CSV / JSON手入力の選択式）自体は
PR #90で既に実装済みでした。今回は、**UI文言とdocsの表現を「JSONで手入力（従来方式）」から
「JSONで手入力（補助的な方法）」に変更**し、CSVが主・JSON手入力が補助という位置づけを
明示しました（内部の処理ロジック・API契約は変更していません）。

## 影響範囲まとめ

### バックエンド
- `backend/app/schemas/ad_insight.py`: `InputModeEnum.FILE_PLUS_KPI`追加、バリデーション分岐追加
- `backend/app/services/credit_pricing.py`: `file_plus_kpi`を`standard`ティア（2クレジット）に追加
- `backend/app/api/routes/specs.py`: `lp_url`フォームパラメータ追加、優先順位ロジック、バリデーション
- `backend/app/cli/main.py`: 開発用CLIツールにも`file_plus_kpi`モードを追加（一貫性のため）
- `backend/app/services/analysis_orchestrator.py`: docstringのモード一覧更新（コードロジックは無変更）

### フロントエンド（Streamlit）
- `frontend/streamlit_app.py`: 「新規分析」タブを CSV→クリエイティブ（複数可）→LP→補助入力 の
  順に再構成。モード選択の既定を標準（推奨）に。LP入力をURL/ファイル選択式に。

### 既存動作への影響
- 既存3モード（`file_only`/`file_plus_lp`/`file_plus_lp_plus_manual_kpi`）の技術的な値・
  バリデーション・クレジット消費量は**変更していません**。
- 既存の`kpi_file`（CSV/JSON振り分け）・`lp_file`（HTML）の挙動も**変更していません**
  （`lp_url`は追加のオプション、未指定時は従来どおり`lp_file`が使われます）。
- 既存テストはすべてパスすることを確認済み（回帰なし）。

## 副次的に発見・修正した重大バグ: ログイン後の認証ヘッダー消失

> **follow-up整理済み**: 今回の修正内容の要約に加え、まだ残っている論点
> （セッション無効時の再ログイン導線が無い、ページリロードでのログイン状態消失、
> テスト不足領域等）を優先度付きで整理しました。
> [auth_state_hardening.md](./auth_state_hardening.md) を参照してください。

実ブラウザでの新UIの動作確認中（ファイルアップロード自体はブラウザツールに機能が
無いため、ページ内でファイル入力へ直接ファイルを割り当てるJavaScriptを使って
擬似的にアップロードを再現した）、**新規導線に限らず、ログイン後のあらゆる
認証必須API呼び出しが、ログイン直後の1回のrerunを過ぎると必ず401になる**
という重大な既存バグを発見しました。

**原因**: `frontend/streamlit_app.py`の`api_session`（全APIリクエストで使い回す
`requests.Session`）が、ファイルの先頭でモジュールレベル変数として
`api_session = requests.Session()` と定義されていました。Streamlitはウィジェット
操作のたびにスクリプト全体を再実行するため、ログイン直後の`api_headers_set(token)`で
一度だけAuthorizationヘッダーをセットしても、次のrerun（タブ切替・入力・ファイル
アップロードなど、何でもよい）でこの行が再実行され、ヘッダーの入っていない
真新しい`Session`に置き換わってしまい、以降のすべてのAPI呼び出しが認証エラーに
なっていました。加えて、モジュールレベル変数は同一プロセスを共有する全ブラウザ
セッションで共通のため、複数社が同時利用する招待制ベータでは、他社のログイン
トークンが自分のリクエストに混入しうるという安全性の問題も併せ持っていました。

**なぜ今まで見つからなかったか**: 自動テスト（pytest）はFastAPI側をTestClientで
直接叩くためStreamlitのrerunモデルを経由せず影響を受けない。過去セッションの
実ブラウザ確認は、ブラウザツールにファイルアップロード機能が無かったため
「分析実行」ボタンを実際に押すところまで到達したことがなく、この経路が
一度も実地検証されていませんでした。今回、JS経由でのファイル入力を編み出した
ことで初めて発覚しました。

**修正**: `api_session`を`st.session_state`（ブラウザセッションごとに独立し、
rerunをまたいで保持される）に保持するよう変更し、モジュールレベルの`api_session`
という名前はrerunのたびに`st.session_state`内の同一オブジェクトを指すように
変更しました。17箇所ある既存の`api_session.*`呼び出しは無変更で動作します。
加えて、ログイン済み判定の分岐で毎rerunヘッダーを保持中のトークンへ揃え直す
二重の安全策も追加しました。

修正後、実ブラウザで「CSV + クリエイティブ + LP」を含む複数のrerunを経てからの
分析実行が実際に200 OKで完了し、クレジットが正しく1消費されること
（`list-usage`で`0/1000`→`1/1000`）まで確認済みです。
