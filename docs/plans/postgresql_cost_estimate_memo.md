# PostgreSQL配置コスト概算メモ（[Issue #80](https://github.com/nario0715masa0619-create/ad-insight-spec/issues/80) 向け）

[`postgresql_hosting_decision_memo.md`](postgresql_hosting_decision_memo.md)で比較した案A（VM同居）・案B（Cloud SQL）について、
**コスト面の判断材料**を追加整理したもの。金額はすべて**確認時点（2026年7月）の公開情報ベースの概算**であり、
実際の請求額を保証するものではない。GCPリソースの作成・API有効化は一切行っていない。

---

## 1. 前提

- 本番: GCP VM `instance-20260626-073827`（`asia-northeast1-a`）、マシンタイプ**e2-medium**（2vCPU/4GB RAM）、ブートディスク**10GB**
- 現在の運用DB: SQLite、実ファイルサイズ712KB（確認時点）
- 想定トラフィック規模: CLAUDE.md記載の内容から、小規模・低頻度アクセスの前提と判断（正確なリクエスト数は未確認）
- 為替: 概算のため1USD=150円で参考換算（変動しうる。正式判断はUSD建てで行うことを推奨）

## 2. 試算条件

- Cloud SQLのregionは本番VMと合わせて`asia-northeast1`（Tokyo）を想定
- ストレージはCloud SQLの最小許容量である**10GB**を基準に試算（GCP公式ドキュメントで確認済み: 10GB未満には設定不可）
- 価格情報の出典は米国`us-central1`基準の公開情報が中心。**Tokyo（asia-northeast1）はus-central1より概ね20〜40%高い**という一般的な傾向を踏まえ、上振れ側を織り込んだレンジで示す
- ネットワーク（VM⇄Cloud SQL間）は同一リージョン内のPrivate IP接続を前提とすれば、追加費用はごく小さいと想定（GCPの一般的な課金体系に基づく推測であり、本メモでは精査していない）

## 3. Cloud SQL 概算（月額、案B）

| 構成 | 内容 | us-central1基準（月額） | Tokyo概算レンジ（月額、+20〜40%） |
|---|---|---|---|
| **最小** | `db-f1-micro`（共有コア, 1vCPU/0.6GB RAM）+ 10GB SSD + 最小限のバックアップ、非HA | 約$8(compute) + 約$2.2(storage) + 約$1.1(backup) ≈ **$11** | **約$13〜16** |
| **現実的最小** | `db-g1-small`（共有コア, 1vCPU/1.7GB RAM）+ 10GB SSD + バックアップ、非HA | 約$26(compute) + 約$2.2(storage) + 約$1.1(backup) ≈ **$29** | **約$35〜41** |
| （参考）専用コア最小 | `db-standard-1`相当（専用1vCPU/3.75GB）+ 10GB SSD、非HA | 約$49(compute) + 同上ストレージ ≈ **$52** | **約$62〜73** |

参考換算（1USD=150円、あくまで目安）:
- 最小: 約**¥1,950〜2,400/月**
- 現実的最小: 約**¥5,250〜6,150/月**
- 専用コア最小: 約**¥9,300〜10,950/月**

**注意点（不明点は不明と明記）**:
- 共有コア（`db-f1-micro`/`db-g1-small`）は**Cloud SQL標準SLA対象外**、かつ確約利用割引（CUD）の対象外。本番運用としては「最小」構成はコスト最優先の選択肢であり、可用性面での妥協を伴う
- 実際のTokyo料金・最新の価格改定は未検証。意思決定用の**レンジ**として扱うこと
- HA構成（ゾーン冗長）にする場合はcompute費用がほぼ倍増する（本メモでは非HA前提のみ試算）
- 実際のバックアップ保持期間・世代数によりバックアップ費用は変動する（ここでは10GB相当・約$0.11/GBで概算）

## 4. VM同居案（案A）との比較

**「追加GCP請求がほぼ増えない」という想定には、今回の確認で1点の留保が必要と判明した。**

本番VMのディスクを読み取り専用で確認したところ:

```
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1       9.7G  7.2G  2.0G  79% /
```

- **ブートディスクは10GBで、既に79%使用・空き2.0GBのみ**
- PostgreSQL本体＋データディレクトリ＋WALログを同居させる余裕は限定的
- メモリは3.8GB中3.1GB利用可能で余裕あり（こちらは問題になりにくい）

このため、案Aは「追加コストほぼゼロ」ではなく、**ディスク拡張（例: +10〜20GB）が実質的に必要になる可能性が高い**。
GCPの永続ディスク追加コストは種別により概ね$0.04〜0.17/GB/月程度とされ、+10GBなら**月額$0.4〜1.7程度**の増加に収まる見込み
（ディスク拡張自体は一般に無停止で実施可能だが、今回は実施していない未検証の推測）。

| 項目 | 案A（VM同居＋ディスク拡張） | 案B（Cloud SQL・最小） |
|---|---|---|
| 追加月額コスト目安 | 約$0.4〜2（ディスク拡張分のみ） | 約$13〜16（最小）〜$35〜73（現実的最小〜専用コア） |
| コスト差 | ほぼ無視できる水準 | **月$10〜70程度の増加** |

## 5. 非コスト要因の比較（[postgresql_hosting_decision_memo.md](postgresql_hosting_decision_memo.md)から要約）

| 観点 | 案A | 案B |
|---|---|---|
| 運用責務 | バックアップ・パッチ・監視を自前運用 | GCPが自動化 |
| 障害切り分け | VM障害がDB/アプリ両方に波及 | DBとアプリの障害を分離できる |
| 「サンプルDATABASE_URL放置」事故の再発防止 | 弱い（`localhost`が書けてしまう） | 強い（実在ホストが必須） |
| 本番ディスクの逼迫リスク | **今回新たに判明**: 現状でも既に79%使用、Postgres追加で拡張がほぼ前提になる | 影響なし（Cloud SQL側の独立ストレージ） |

## 6. 結論

- **Cloud SQL（案B）の概算月額は、最小構成で約$13〜16（¥2,000弱）、可用性をある程度確保する現実的な構成で約$35〜73（¥5,000〜11,000程度）**
- 案Aは金額だけ見れば圧倒的に安いが、**現状の本番ディスクが既に79%使用・空き2GBという事実が今回判明**しており、
  「ほぼ追加コスト無し」という前提には注意が必要（ディスク拡張自体の追加コストは小さいが、運用上の手間は発生する）
- 月額$15〜75程度（構成次第）を許容できるなら、案Bは事故再発防止・運用責務分離のメリットと引き合う水準と考えられる
- 逆にこの金額でも許容が難しい場合、案Aを選びつつ「サンプルDATABASE_URL放置」事故の再発防止策（例: `.env`のDATABASE_URL変更時のチェックリスト運用、または`db/session.py`側での起動時ヘルスチェック強化）を別途講じる方向性が現実的

**このコストなら案Bを採るべきか、という問いへの一次的な回答**: 最小構成（月$13〜16程度）であれば、既存本番のディスク逼迫状況も踏まえると、
**コスト以上のリスク低減効果が見込めるため、案Bへの前進は妥当な選択肢**と考えられる。ただし最終判断は、実際の予算許容度という
未確認事項に依存する。
