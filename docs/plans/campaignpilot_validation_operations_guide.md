# CampaignPilot 実査運用ガイド

[`campaignpilot_business_validation_plan.md`](campaignpilot_business_validation_plan.md)（検証仮説・成功/失敗条件・全体設計）を
実際に**回せる手順**まで落としたもの。対象読者は、実査を担当する人（開発者本人とは限らない）。
このガイドだけを見れば、次に何をすればよいか迷わない状態を目指す。

対象Issue: [#87](https://github.com/nario0715masa0619-create/ad-insight-spec/issues/87)

---

## 1. 背景

事業検証プラン（[campaignpilot_business_validation_plan.md](campaignpilot_business_validation_plan.md)）で、
検証仮説（H1〜H4）・成功/失敗条件・全体の実査フローの骨格は定義済みである。

しかし、そのドキュメントは「何を検証するか」の設計であり、「実査担当者が案件ごとに何をいつ聞き、
どこに記録するか」という**実務手順**までは踏み込んでいない。本ガイドはその手順を埋める。

## 2. 実査運用の目的

- 3〜5件の実査を、担当者が迷わず・条件を揃えて回せる状態にする
- verification機能に記録する情報と、手元メモで補う情報を明確に分け、記録漏れ・記録先の迷いを無くす
- 案件ごとの結果を、H1〜H4という同じ物差しで比較できる形にする
- 実査がうまくいかなかった場合に、「プロダクトの価値不足」なのか「案件・対象者の選定ミス」なのかを
  切り分けられるようにする

---

## 3. 対象案件の選定基準（チェックリスト）

以下をすべて満たす案件のみを実査対象とする。1件でも満たさない項目があれば、その時点で候補から外す
（または満たすまで調整する）。

- [ ] **直近運用実績**: 直近30日以内にMeta広告の運用実績があり、KPIデータ（インプレッション・クリック・CVR等）が取得できる
- [ ] **ヒアリングアクセス**: 運用担当者から、事前ヒアリング・提示後評価・週2回程度のフォローアップ（計3〜4回、各15〜30分程度）の時間を確保できる見込みがある
- [ ] **経済購買者アクセス**: 費用の意思決定者（運用担当者と別人の場合はその人）へのヒアリングアクセスが見込める、または運用担当者自身が意思決定者を兼ねることが確認できている
- [ ] **未認知**: その案件の担当者が、CampaignPilotの存在や提案内容を事前に知らない（新規性評価が歪まない）
- [ ] **非開発チーム案件**: 開発チーム自身が運用している案件ではない（自己評価バイアスを避ける）

以下は**絶対条件ではなく緩い目安**（3〜5件全体でのバランスを見る）:

- [ ] 業種・広告予算規模が、既に選定済みの他の案件と極端に偏っていない

**選定手順**:
1. 上記条件に照らして、まず8〜10件程度の候補をリストアップする（母集団化）
2. その中からチェックリストをすべて満たす3〜5件に絞る
3. 絞り込みで悩む場合は、業種・予算規模の分散を優先する

---

## 4. 対象者と役割

| 役割 | ヒアリングする内容 | いつ聞くか |
|---|---|---|
| **運用者** | 事前の課題認識、提示後の評価、提案ごとの気づき度/独自性、実行有無、成果/工数の体感 | 全フェーズ（必須） |
| **マネージャー** | 担当者交代時の引き継ぎやすさ、チーム内の判断のばらつきへの影響 | 可能であれば事前ヒアリングと実査完了後の総括時（任意） |
| **経済購買者** | 成果差・工数削減の金額換算、継続利用への支払い意思 | 実査完了間際（week_4前後）に必須で実施 |

運用者と経済購買者が同一人物の場合でも、**質問セットを分けて聞く**（「使ってみてどうでしたか」と
「これにお金を払いますか」は別の質問であり、同じ回答にならないことがある）。

---

## 5. 実査の標準フロー

```
Step 1: 案件候補の母集団化（8〜10件程度）
Step 2: 選定条件（3章）で3〜5件に絞る
Step 3: 事前ヒアリング（運用者、必要ならマネージャーにも）
Step 4: CampaignPilot提示と提案評価（運用者）
Step 5: 実行有無の中間追跡（week_2前後）
Step 6: week_2 / week_4 の成果・工数確認
Step 7: 経済購買者への課金意思確認（week_4前後）
Step 8: 案件ごとの暫定判定（H1〜H4を仮判定）
Step 9: 全体横断でのgo/no-go判断（3〜5件がすべて完了した時点）
```

Step 3〜7が「1案件あたりの運用フロー」（7章で詳細化）。Step 8〜9は全案件が出揃ってからの集計作業。

---

## 6. 各フェーズでの確認事項（1案件あたりの運用フロー）

実査担当者は、1つの案件についてこのチェックリストを上から順に実施する。

### Step 3: 事前ヒアリング
- [ ] 運用者に、現状の課題認識をヒアリングする
- [ ] Meta広告の運用歴・現状の運用体制をヒアリングする
- [ ] CampaignPilotに何を期待しているかをヒアリングする
- [ ] **`POST /api/v1/verification/cases`** で案件を作成し、上記をJSONで記録する
      （`case_name`, 既存分析結果があれば`asset_id`+`asset_version`, `pre_hearing_notes`）
- [ ] 経済購買者が誰か（運用者と同一か別人か）をこの時点で確認し、手元メモに記録する（8章）

### Step 4: CampaignPilot提示と提案評価
- [ ] CampaignPilotの分析結果を運用者に提示する
- [ ] 提示直後の全体的な有用度・コメントを聞く（社交辞令が混じりやすい参考値と割り切る）
- [ ] **`PATCH /api/v1/verification/cases/{id}/presentation-evaluation`** で記録する
- [ ] 提示された提案を1つずつ、**運用者自身の言葉で**次を確認する:
  - 「これは前から気づいていましたか、それとも今言われて気づきましたか」（気づき度）
  - 「これは自分でも思いついていましたか」（独自性）
- [ ] 提案ごとに **`POST /api/v1/verification/cases/{id}/suggestions`** で記録する
      （`suggestion_key`は提案タイトルを短く、`suggestion_text`は提案内容をそのままコピー、
      `awareness_rating`/`originality_rating`は運用者の回答に最も近い選択肢を選ぶ。
      **実査担当者の主観で選ばない**）

### Step 5: 実行有無の中間追跡（週1回程度の軽い確認でよい）
- [ ] 提案ごとに、実行に着手したか／着手予定かを軽く確認する（正式な記録はStep6で行う）
- [ ] この時点で「実行できない」と分かった提案があれば、理由（優先度が低い／権限がない／技術的に難しい等）を手元メモに残しておく（10章の切り分けに使う）

### Step 6: week_2 / week_4 の成果・工数確認
- [ ] （2週間後）提案ごとに実行有無を確認する
- [ ] （2週間後）実行された提案について、成果変化（自由記述）を聞く
- [ ] **`PUT /api/v1/verification/suggestions/{id}/followups/week_2`** で記録する
- [ ] （4週間後）同様に実行有無・成果変化を確認し、**`.../followups/week_4`** で記録する
- [ ] （4週間後）運用者に、CampaignPilot導入前と比べて「判断にかかる時間」がどう変わったかを聞く
      （増えた／変わらない／減った、可能なら「週あたり何時間相当」の体感値）→ 手元メモに記録（現状スキーマ外）

### Step 7: 経済購買者への課金意思確認
- [ ] （week_4前後）経済購買者に、成果/工数の変化を踏まえて「これに対価を払う意思があるか」を直接聞く
- [ ] Yes / No / 条件付き（条件の内容）で手元メモに記録する
- [ ] 「今の内容なら有償でも使い続けたいか」（継続意思）も同時に聞き、手元メモに記録する

### Step 8: 案件ごとの暫定判定
- [ ] この案件単独で、H1〜H4それぞれを「成立／不成立／中間」で仮判定する（9章の方法に従う）
- [ ] 不成立の仮説があれば、10章の切り分け表に照らして暫定的な原因を記録する

## 7. verification機能への記録ルール

| タイミング | API | 記録する内容 |
|---|---|---|
| 事前ヒアリング直後 | `POST /api/v1/verification/cases` | 案件名、関連asset_id/asset_version（あれば）、事前ヒアリング内容 |
| 提示直後 | `PATCH /cases/{id}/presentation-evaluation` | 全体的な有用度、コメント |
| 提案ごと | `POST /cases/{id}/suggestions` | 提案タイトル・内容のコピー、気づき度、独自性（提案1件につき1回呼ぶ） |
| 2週間後 | `PUT /suggestions/{id}/followups/week_2` | 実行有無、成果変化（自由記述） |
| 4週間後 | `PUT /suggestions/{id}/followups/week_4` | 実行有無、成果変化（自由記述） |

**記録ルール**:
- `awareness_rating`/`originality_rating`は、実査担当者の解釈ではなく、運用者本人の発言に最も近い選択肢を選ぶ
- `suggestion_text`は要約せず、提案内容をできるだけそのままコピーする（後から新規性を再評価できるようにするため）
- 案件を作成したら、その`id`（数値）を手元メモの先頭に必ず控える（8章のメモとverification記録を後で突き合わせるため）

## 8. 手元メモで補う項目（現状のverification機能のスキーマには専用フィールドが無い）

以下は、verification機能に記録できないため、案件ごとに簡単な表（スプレッドシート等、形式は問わない）で
別途管理する。**この段階でスキーマ拡張は行わない**（実査を先に回し、必要性が確認できてから検討する）。

| 項目 | 記入タイミング | 記入内容の例 |
|---|---|---|
| verification `case_id` | 案件作成直後 | 後でverification側の記録と突き合わせるための必須キー |
| 経済購買者の役職/立場 | 事前ヒアリング時 | 例: マーケ責任者、運用担当者本人が兼任 等 |
| 実行障壁の理由（実行されなかった場合） | Step5, Step6 | 例: 優先度が低い、権限がない、技術的に難しい 等 |
| 工数削減の自己申告 | week_4 | 例: 「週2時間相当の判断時間が減った」（定性・定量どちらでも可） |
| 課金意思 | week_4前後 | Yes / No / 条件付き＋条件の内容 |
| 継続意思 | week_4前後 | Yes / No / 条件付き＋条件の内容 |
| ヒアリング実施日・実施者 | 各フェーズ | 記録の信頼性確認用 |

## 9. H1〜H4の判定方法（判定タイミング表）

| 仮説 | 判定に使うデータ | 判定タイミング | 判定基準（目安） |
|---|---|---|---|
| **H1 新規性** | `originality_rating`（verification記録） | Step4（提案評価記録時点） | `could_not_have_suggested_myself`が1件以上あれば「成立」の芽。全提案が`generic`中心なら「不成立」 |
| **H2 実行** | `VerificationFollowup.executed`（verification記録） | Step6（week_2で仮判定、week_4で確定） | H1が成立した提案のうち、実行されたものがあれば「成立」 |
| **H3 成果/工数** | `result_change`（verification記録）＋工数自己申告（手元メモ） | Step6 week_4時点 | 実行された提案について、成果差または工数削減の体感が確認できれば「成立」 |
| **H4 課金意思** | 課金意思・継続意思（手元メモ） | Step7（week_4前後） | 経済購買者からYesまたは条件付きYesが得られれば「成立」 |

各案件についてStep8で仮判定し、3〜5件が揃った時点（Step9）で、事業検証プランの
[9章「有償パイロット判定条件」](campaignpilot_business_validation_plan.md#9-有償パイロット判定条件)に照らして全体判定を行う。

## 10. 実査失敗時の切り分け方

ある案件・ある仮説が「不成立」だった場合、原因を以下の観点で切り分ける。
**1件だけ不成立で他の案件は成立している場合は「案件・対象者側の要因」を疑い、
複数案件で同じ仮説が繰り返し不成立になる場合は「プロダクト側の要因」を疑う**、という判断軸を基本とする。

| 症状 | 主な切り分け | 記録・対応の方向性 |
|---|---|---|
| H1が弱い（提案が一般論中心） | 提案の新規性不足（プロダクト要因の可能性） | 複数案件で共通なら、分析ロジック・提案の作り方の見直し課題として記録（今回のスコープではコード変更しない） |
| H2が弱い（H1は成立するが実行されない） | 提案はよいが実行障壁が高い（運用体制側の要因の可能性） | Step5で記録した実行障壁の理由（権限・優先度・技術難度）を確認し、プロダクト要因か運用側要因かを分ける |
| H3が弱い（実行されたが成果/工数に効かない） | 提案の優先順位付けや粒度の問題（プロダクト要因の可能性） | 「気づける」ことと「効果が出る」ことは別の力学であることを踏まえ、優先順位ロジックの課題として記録 |
| H4が弱い（H1〜H3は成立するが課金意思がない） | 価値はあるが価格/ROI設計が弱い（ビジネスモデル要因、プロダクト自体の欠陥ではない） | 価格設定・訴求方法の課題として記録し、プロダクトの作り直しとは切り離す |
| 他の案件と比べて明らかに傾向が違う1件だけ弱い | 案件・対象者選定のミスの可能性 | 3章の選定基準を満たしていたか再確認する。満たしていなければその案件を参考値扱いとし、必要なら代替案件を追加する |

## 11. 実査完了後に必要な意思決定

3〜5件すべてでStep8（案件ごとの暫定判定）まで完了したら、Step9として:

1. 全案件のH1〜H4判定結果を並べ、事業検証プランの有償パイロット判定条件と照合する
2. 10章の切り分けに従い、不成立だった仮説が「プロダクト要因」「運用側要因」「案件選定要因」のどれに
   起因するかを整理する
3. 事業検証プランの結論区分（A. 有償パイロットへ進む／B. 提案内容・提示方法を見直して再実査／
   C. 機能の作り方自体を見直す）のいずれに該当するかを判断する
4. Issue #87 に結果を記録し、クローズまたは次フェーズへの引き継ぎを行う

**最終的な有償パイロット可否の判断は、費用対効果を最終的に負う立場（経済的な意思決定者）が行う。**
実査担当者はここまでの整理を揃えるところまでが役割であり、go/no-goの決定自体はスコープ外とする。
