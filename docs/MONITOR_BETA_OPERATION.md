# モニターベータ運用ガイド

CampaignPilot を「招待制・月間利用上限つきのモニターベータ」として、少数（3〜5社程度）の
モニター企業に外部公開するための運用ガイドです。対象読者は、モニター企業の担当者、
および社内でモニター対応をする担当者です。

管理者向けのアカウント発行・上限変更などの操作手順は
[MONITOR_ACCOUNT_MANAGEMENT.md](./MONITOR_ACCOUNT_MANAGEMENT.md) を参照してください。

## 1. モニターベータとは

- CampaignPilot は現在、**一般公開ではなく招待制のベータ版**として提供しています。
- 自由なアカウント登録（セルフサインアップ）はできません。利用開始には、必ず運営側からの
  アカウント発行（招待）が必要です。
- ベータ版のため、画面・機能・分析ロジックは**予告なく変更される場合**があります。
- 気づいた不具合やご意見は、担当者へのフィードバックとしてお寄せいただけると助かります。

## 2. ログイン方法

1. 運営側からメールアドレス・初期パスワードが発行されます（別チャネルで個別に共有されます）。
2. Streamlit UI を開くと、他の画面より先にログインフォームが表示されます。
3. 発行されたメールアドレス・パスワードを入力してログインしてください。
4. ログイン後は画面左のサイドバーに、所属会社名・今月の利用状況・ログアウトボタンが表示されます。

ログインセッションはサーバー側で管理しており、有効期限は発行から2週間です。期限が切れた場合や
アカウントが停止された場合は、次回操作時に自動的に再ログインが求められます。

パスワードの自己リセット機能は今回のスコープでは提供していません。パスワードを忘れた・変更したい
場合は、管理者に再発行を依頼してください（[MONITOR_ACCOUNT_MANAGEMENT.md](./MONITOR_ACCOUNT_MANAGEMENT.md) 参照）。

## 3. 月間クレジット上限

CampaignPilotは「月◯件まで」という単純な件数制ではなく、**月額プラン + 月次クレジット付与**
という考え方で利用上限を管理しています（詳細な設計意図は
[クレジット課金設計案](./campaignpilot_credit_billing_design.md) 参照。今回のモニターベータでは
このうち「会社単位のクレジット管理」「プラン定義の外出し（`pricing_plans`テーブル）」
「3段階固定消費」「月初リセット」「利用履歴」「管理者の手動調整」のみを実装し、
商用プランの販売導線・決済・繰越・追加購入・予約制の状態機械は未実装です）。

- クレジット上限は**会社単位**で設定されています（ユーザー単位ではありません）。同じ会社に
  複数ユーザーがいる場合、全員の消費クレジットが合算されます。
- 実効クレジット上限は次の優先順位で決まります。
  1. **会社ごとの個別上書き** （管理者が特定の会社にだけ設定した値）
  2. **紐づいたプラン**（Starter/Growth/Pro/Monitorなど）の月次クレジット
  3. **既定のフォールバック値**（100クレジット。個別上書きもプランも無い会社向け）

  プラン名・価格・付与クレジット・キャンペーン文言はコードではなく`pricing_plans`
  テーブルで管理しているため、価格改定やプラン内容の見直しをコード変更・再デプロイ
  なしで行えます（操作方法: [MONITOR_ACCOUNT_MANAGEMENT.md](./MONITOR_ACCOUNT_MANAGEMENT.md)）。
  ただし商用プランの一覧を外部に公開する画面（価格表ページ）はまだありません。

  **初期プラン定義**（`scripts/seed_data/pricing_plans.json`、`seed-plans`コマンドで投入）:

  無料モニター枠（正式プランとは分離して管理）:

  | プラン | 月額 | 月次クレジット | 1クレジット単価 | 公開対象 | 位置づけ |
  |---|---:|---:|---:|:---:|---|
  | Monitor Beta | ¥0 | 300 | ¥0 | 非公開 | 招待制モニター企業向けの無料検証枠 |

  正式プラン:

  | プラン | 月額 | 月次クレジット | 1クレジット単価 | 公開対象 | 位置づけ |
  |---|---:|---:|---:|:---:|---|
  | Starter | ¥49,800 | 100 | 約¥498 | 公開 | 小規模な試験導入 |
  | Growth | ¥99,800 | 300 | 約¥332.7 | 公開 | 本格運用の標準プラン |
  | Pro | ¥179,800 | 650 | 約¥276.6 | 公開 | 複数案件・高頻度利用（「初期導入企業向けキャンペーン企画中」） |
  | Enterprise | 個別見積 | 個別設計（初期値1000は仮） | - | 非公開 | 部門導入・横展開。実運用ではほぼ必ず会社側でoverride |

  上位プランほど1クレジット単価が下がる設計です（Starter→Growth→Pro）。ただしProを
  極端に安くしすぎないよう、650クレジットで抑制しています。

  モニター企業には基本的に `Monitor Beta` プランを割り当てます（`code: monitor`、
  無料の検証専用枠）。`Starter/Growth/Pro`は商用提供向けの正式プランで、モニター運用中は
  基本使いません（商用移行時に割り当てを切り替える想定）。plan/override の使い分けの詳細な運用ルールは
  [MONITOR_ACCOUNT_MANAGEMENT.md](./MONITOR_ACCOUNT_MANAGEMENT.md) の「2-2. plan と
  override の使い分けルール」を参照してください。
- 分析を実行すると、**分析内容に応じて1〜3クレジット**を消費します。

  | 分析内容 | 消費クレジット |
  |---|---:|
  | クリエイティブのみ（file_only、最小・簡易） | 1 |
  | クリエイティブ + LP（file_plus_lp、数値なし・簡易） | 2 |
  | クリエイティブ + CSV/KPI（file_plus_kpi、LPなし・広告面分析） | 2 |
  | クリエイティブ + LP + CSV/KPI（file_plus_lp_plus_manual_kpi、**標準・推奨**） | 3 |

  この消費量は環境変数（`CREDIT_COST_LIGHT` / `CREDIT_COST_STANDARD` / `CREDIT_COST_HEAVY`）で
  調整可能です。コードを変更せずに運用側で見直せます（詳細:
  [MONITOR_ACCOUNT_MANAGEMENT.md](./MONITOR_ACCOUNT_MANAGEMENT.md)）。
- **消費が確定するのは分析が成功した時のみ**です。「実行前チェック→成功時のみ消費確定」という
  シンプルな方式を採用しており、同時実行時の厳密な二重消費防止や、失敗時の返却状態を細かく
  管理する「予約(reserved)」の仕組みは今回のスコープでは持ちません（3〜5社規模のベータでは
  過剰な作り込みと判断したため。将来の商用化フェーズでの再検討候補です）。
  - システムエラーや分析不成立などで失敗した場合、クレジットは一切消費されません。
  - 逆に、成功して保存された分析結果を後から論理削除しても、消費済みクレジットは戻りません。
- 上限は**毎月1日 00:00 (UTC) にリセット**されます。「登録日から30日」のような起算方式ではありません。
  リセットは実際にはバッチ処理ではなく、「当月1日以降に消費が確定した分の合計」を都度集計する
  方式で実現しているため、リセット処理自体が失敗するということが原理的に起こりません。
- 画面左のサイドバーに「今月のクレジット利用 / 上限」「残りクレジット」が表示されます。分析実行の
  たびに更新されます。分析実行前にも、そのモードで消費される目安のクレジット数が表示されます。
- 上限に到達すると（正確には、残クレジットがその分析の消費量に満たない場合）、分析実行ボタンを
  押した際にエラーメッセージが表示され、新規分析はブロックされます。追加の利用枠が必要な場合は
  管理者にお問い合わせください。

## 4. データの取り扱い・分離

- アップロードした広告クリエイティブ・LP・KPIデータ、および分析結果は、**自社のアカウントでログインした
  ユーザー間でのみ共有**されます。他社のモニター企業の分析結果が見えることはありません。
- 「保存済み結果」一覧・詳細画面・削除操作は、いずれも自社（ログイン中ユーザーの所属会社）が
  作成した分析結果のみを対象とします。

### 既知の制約（今回のスコープでの割り切り）

- **既存データ（招待制導入前に作成された分析結果）** は会社に紐付いていないため、
  招待制導入後はどのモニター企業の一覧にも表示されません（データが消えたわけではなく、
  単に新しいスコープの外にあるだけです）。
- **`asset_id` は会社をまたいでグローバルに一意**という前提のままです。`asset_id` は
  アップロードファイルの内容から生成されるハッシュを含むため、異なる会社が同じ`asset_id`を
  取得する確率は実運用上ごく僅かですが、理論上ゼロではありません。将来的に会社数が増える場合は
  `asset_id`の会社単位での名前空間化を検討してください。
- **「検証」タブ（`/api/v1/verification/*`）はログイン必須にしていますが、会社単位のデータ分離は
  行っていません。** これは社内QA・仮説検証用の機能であり、モニター企業向けの主要フローではないため、
  今回のスコープでは「ログインしていれば誰でも見える」という割り切りにしています。モニター企業に
  この機能を触らせる運用にする場合は、別途データ分離の実装が必要です。
- **プランは商用販売の構造だけを用意しており、販売導線・価格表ページ・決済は未実装です。**
  `pricing_plans`テーブルにStarter/Growth/Pro等を登録できますが、それを外部向けに表示する
  画面はまだありません。
- **会社が存在しないプランID（削除済み等）を指している場合、エラーにはせず静かにフォールバック
  値へ倒します。** 運用上は「プランを削除する」操作自体を用意していない（`is_active=false`で
  無効化するのみ）ため通常は発生しませんが、直接DBを操作した場合などの保険的な挙動です。
- **クレジット消費の実行前チェックと消費確定の間に排他制御（ロック）がありません。**
  `has_sufficient_credits()`と`record_credit_usage()`は独立した2回のDBアクセスであり、
  同一会社に対する`/analyze`が同時に複数実行された場合、両方が「残量あり」と判定してから
  両方とも消費を確定してしまい、結果として上限をわずかに超過する可能性があります
  （例: 残り1クレジットの状態で2件が同時に実行されると、消費後の合計が2になり得ます）。
  これは見落としではなく、3〜5社規模のモニターベータでは同時実行の衝突頻度が実務上
  無視できる水準であるという判断のうえで、意図的にスコープ外にしています。将来、
  会社数や同時利用者数が増えてリスクが無視できなくなった場合は、
  DBレベルの行ロック（`SELECT ... FOR UPDATE`相当）・トランザクション分離レベルの強化・
  クレジット課金設計案にある「予約(reserved)→確定/返却」の状態機械の導入、といった
  対応を検討してください（詳細: [クレジット課金設計案](./campaignpilot_credit_billing_design.md)）。

## 5. モニター利用者からよくある質問

**Q. パスワードを変更したい**
A. 自己変更機能は現状ありません。管理者にパスワード再発行を依頼してください。

**Q. クレジットを使い切ってしまった。今月中に追加で分析したい**
A. 管理者にクレジット上限の引き上げを依頼してください（[MONITOR_ACCOUNT_MANAGEMENT.md](./MONITOR_ACCOUNT_MANAGEMENT.md) の「4. クレジット上限を変更する」参照）。

**Q. 分析が失敗した。クレジットは消費されますか**
A. されません。クレジットは分析が成功した場合にのみ消費が確定します。

**Q. 同じ会社の同僚にもアカウントを発行してほしい**
A. 管理者にメールアドレスを伝えて招待を依頼してください。

**Q. Meta Ads CSVはどう使えばいいですか**
A. 「新規分析」タブで分析パターン「🌟 標準（推奨）: CSV + クリエイティブ + LP」
（LPが無い場合は「CSV + クリエイティブ（LPなし・広告面分析）」）を選び、①のセクションで
KPI入力方法として「Meta Ads CSV（そのままアップロード・推奨）」を選択し、Meta Ads Manager
からエクスポートしたCSVをそのままアップロードしてください。列の並べ替えや削除は不要です
（詳細: [META_ADS_CSV_IMPORT.md](./META_ADS_CSV_IMPORT.md)）。「標準（推奨）」は3クレジット、
「LPなし・広告面分析」は2クレジットを消費します。
